# R-01 調査メモ(方針決め: 土台・ログイン・4 役割・メニュー)

## 要約

- リポジトリにアプリのコード・ビルド設定・技術の手がかりはない。あるのは docs と .jigwork-issues と README.md だけである。
- docs の雛形 5 つ(overview・nfr・glossary・architecture・screen-rules)は見出しだけである。実質の入力は docs/spec.md だけである。
- 仕様は、ログインと認証の方式・利用者の登録・部署・複数の役割を書いていない。
- 技術は決まっていない。/base のテストの手順は `cd backend && uv sync --frozen --no-build` で始まる(backend は Python と uv を前提にしている)。
- 規模の見込みは、土台とログインと役割とメニューで約 650〜1,250 行である(推定)。500 行を超える公算が高い。

## 2. 影響範囲(すべて新規)

- 画面: ログイン画面・ログアウト・役割ごとのメニュー。メニューの先は、この Issue では未実装の表示になる。
- 帳票: なし。
- API: ログイン・ログアウト・ログイン中の利用者と役割の取得。
- テーブル: 利用者・役割・利用者と役割の対応・部署(上長の判断に要るなら)。仕様は、全テーブルと全列の日本語の論理名コメントと、テーブル番号(T001 の形)とテーブル定義書(Excel)を求める(spec.md:43-44)。
- バッチ: なし。
- 外部連携: なし。外部のメールとクラウドの認証は使わない(spec.md:46)。
- 設定: DB の接続・セッション・4 役割の試験用の利用者の初期データ。秘密の情報を入れない(spec.md:46)。
- 権限: 役割とメニューの表示の対応。権限のない画面を URL の直打ちで開けないようにするかは決めていない。
- 文書: overview・nfr・architecture・screen-rules・glossary・docs/README.md。
- テスト: 4 役割それぞれのログインの成功とメニューの中身、ログインの失敗、未ログインの扱い。

## 3. 仕様の記述と穴

仕様にあること:

- 役割は 4 つである(spec.md:9-12)。社員は依頼と取り消し、上長は自部署の依頼の決裁と差し戻し、購買担当は発注と入荷、管理者は仕入先・区分・利用者と役割の管理である。
- 利用者は約 120 人、部署は 3 つ、倉庫は 1 つである(spec.md:7)。
- スマホでは決裁と入荷の 2 つが使えれば足りる(spec.md:45)。

穴:

- 認証の方式(ID とパスワードか、社内のディレクトリか)。
- 利用者の登録の方法と初期データ(管理者の画面か、一括の取り込みか)。
- パスワードの規則(初期値・変更・忘れたとき・ロック)と、秘密の情報を入れない制約との整合。
- 上長と部署の関係、代理の決裁者。
- 1 人が複数の役割を持つか。上長が自分の依頼を決裁できるか。
- スマホでのログインとメニューの要否。
- セッションの期限・監査のログの要否。
- メニューの項目の一覧と、押した先の動き。

## 4. 用語

- 用語集は空である。登録の候補は、社員・上長・購買担当・管理者・役割・利用者・ログイン・メニューである。
- 同じ概念に複数の語がある: 「利用者」と「使う人」、「役割」と「ロール」(overview.md の見出し)。「社員」は役割の名前と全従業員の意味の両方に読める。

## 5. 規模と分割の案(推定)

- 土台約 150〜300 行、ログインとセッション約 150〜250 行、テーブルと初期データ約 100〜200 行、メニュー約 100〜200 行、テスト約 150〜300 行である。
- 分割の案:
  1. 要件の確認と文書(技術の選定と認証の方式を決めて書く。コードの差分は 0)。
  2. プロジェクトの土台(雛形・DB の接続・テストの枠)。
  3. 利用者・役割・部署のテーブルと初期データ、ログインとログアウト。
  4. 役割ごとのメニューと、権限のない画面の拒否。
