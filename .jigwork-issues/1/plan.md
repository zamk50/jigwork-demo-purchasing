# plan.md

## 理解の要約

総務部の依頼で、仕様概要(docs/spec.md)の購買と在庫のシステムを作り始める。
この Issue の目的は、システムの土台を作ることである。
あわせて、4 つの役割の利用者がログインして役割ごとのメニューを使えるようにする。
仕様の分からない所は、要件定義で依頼元に確かめる。
要件定義書と設計書を書いてから実装する。
業務の機能(依頼・決裁・発注・入荷・在庫・帳票・夜間の処理)は後の Issue で作る。

## スコープ

- ログインと役割に関わる仕様の穴を依頼元に確かめ、要件定義書に書く。
- 要件定義で確かめる穴は、前提一覧の 🟡 に挙げた項目である。
- docs/spec.md の位置づけ(正本か、入力の資料か)を要件定義で決める。
- フレームワーク・DB・テストの手順と認証の方式を、方式設計に書く。
- アプリの土台(backend のプロジェクト・DB の接続・テストの枠)を作る。
- アプリの ID とパスワードでログインとログアウトをできるようにする。
- パスワードはハッシュで保存する。
- 利用者・役割・利用者と役割の対応・部署のテーブルを作る。
- テーブルと列には日本語の論理名のコメントを付ける。
- テーブルには依頼元のテーブル番号(T001 の形)を付ける。
- 4 つの役割(社員・上長・購買担当・管理者)の試験用の利用者を初期データで入れる。
- 役割ごとのメニューを出す。メニューの先の業務の画面は「未実装」と表示する。
- 権限のない画面を URL の直打ちで開いたときは拒否する。

## スコープ外

- 管理者が利用者と役割を登録・変更する画面(後の Issue)。
- 業務の機能(品目・購入依頼・決裁・発注・入荷・在庫・夜間の処理)。
- 価格表の取り込み・会計の CSV・月次の集計(後の Issue)。
- 社内のディレクトリ(AD・LDAP)とクラウドの認証による認証。
- パスワードを忘れたときの再発行の画面。扱いは要件定義で決める。画面は後の Issue で作る。
- テーブル定義書の Excel。jigwork の B3 の段で延ばした部品であり、この Issue ではテーブルを設計書の文で書く。

## 受入基準

- AC-01 社員・上長・購買担当・管理者の試験用の利用者が、それぞれ ID とパスワードでログインできる。
- AC-02 ログインした利用者のメニューに、その役割に割り当てた項目だけが出る。
- AC-03 誤った ID かパスワードではログインできず、ログイン画面にエラーが出る。
- AC-04 ログインしていない利用者がメニューか業務の画面の URL を開くと、ログイン画面に移る。
- AC-05 ログインした利用者が権限のない画面の URL を直接開くと、HTTP 403 と拒否の画面が返る。
- AC-06 ログアウトした後にメニューの URL を開くと、ログイン画面に移る。
- AC-07 DB の利用者のテーブルに、平文のパスワードがない。
- AC-08 リポジトリのファイル(初期データを含む)に、試験用の利用者の平文のパスワードがない。
- AC-09 作ったテーブルと列のすべてに、日本語の論理名のコメントが付いている。
- AC-10 作ったテーブルのすべてに、テーブル番号(T001 の形)が付いている。
- AC-11 受付で決めたテストの手順(最初の段は `cd backend && uv sync --frozen --no-build`)が、エラーなしで通る。

AC-02 の役割ごとの項目の表は、要件定義書の機能要件に書く。表のうち業務の項目は「未実装」の表示を出す。

## リスク判定と実施計画

段階は重要(major)である。該当した因子と根拠は次のとおりである。

- intent: Issue は「仕様で分からないところを確かめてから」と求める。仕様の穴は要件定義で確かめる。
- intent は因子の再判定で該当とされ、足した。段階は変わらない。
- visible: 利用者が使う最初の画面(ログイン・メニュー)を新しく作る。
- data: 利用者・役割・部署のテーブルを新しく作る。戻し方を設計に書く。
- auth: 認証と役割による認可を作る。セキュリティの観点のレビューを受ける。
- new: フレームワークと DB を新しく選ぶ。設計で代替案を比べる。
- wide: 差分は約 650〜1,250 行の見込みである([R-01](research/R-01.md) の 5)。
- wide の対処: Issue を分けない(Q-01 の回答)。実装計画でタスクを分ける。

該当しない因子は次のとおりである。

- external: 外部と連携しない(Q-02)。
- commitment: personal では既定でオフである。

## 実施計画の推奨

- 段階: 重要(major)。
- 通すフェーズ: 受付・方針決め・要件定義・設計・実装計画・実装・検証・PR 作成・PR 対応。
- 省くフェーズ: なし。
- ゲート: 方針決め・実装前・PR 作成・最終の承認。
- 承認者: 本人。personal では他者の承認も本人が押す。
- 外部の承認: 要らない。
- マージ先: main。最終の PR を作る。
- 途中の draft PR: 作ることを推奨する。承認の口の該当の画面は jigwork の B5 の段で延ばした。
