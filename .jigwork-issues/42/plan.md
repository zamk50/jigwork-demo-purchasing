# Issue 42 ログインのロックが掛かったことを、ログで見分けられるようにする

## 理解の要約

- 何を: ログインのロックが掛かった時と、ロック中にログインを試みた時に、ふつうの失敗と見分けられる行をログに出す。
- なぜ: 今はどちらも「ログインに失敗した 社員番号=…」の 1 行だけで、運用の担当がロックに気づけないため。
- どこまで: 要件に FR を足し、方式設計のログの決まりを直し、ログの行を出すコードとテストを足す。
- 画面・API の応答・テーブル・ロックの回数と時間は変えない。

## スコープ

- ロックが掛かった時(5 回目の誤り)に、ロックが掛かったと分かる行をログに出す。
- ロック中にログインを試みた時に、ロック中の試みと分かる行をログに出す。
- ロックが掛かった・ロック中の区別を、業務の層 `authenticate`(`backend/app/auth/service.py`)からログの行を出す所へ渡す。渡し方は設計で決める。
- 機能要件「ログインする」(FNC-001、`docs/requirements/functions/FNC-001.md`)に、ロックの行を出す FR を足す(作業者の質問「ロックの行の決まりの置き場」(Q-03)の答え)。
- 方式設計 `docs/internal/architecture.md` の「例外とログ」に、ロックの行の決まりを足す。
- 同じ方式設計の認証の節に、ロックの区別の渡し方を足す。
- ロックの行のテストと、ロックの行にパスワードと印が出ないことのテストを足す。
- コードの説明文(`backend/app/api/auth.py`・`backend/app/log.py` の docstring)を合わせる。実装のレビューで確かめる。

## スコープ外

- ロックの解除(ロックが終わった後の最初の試みで回数を 0 に戻す時)の行は足さない(依頼元の質問「解除の行」(Q-02)の答え)。要るなら別の Issue にする。
- ログインの状態の切れの行は足さない。
- 登録なし・形の誤り・誤ったパスワード(1〜4 回目)・役割なしの失敗は、今の「ログインに失敗した」の行のまま分けない。
- 画面の文と API の応答(401 と共通の文)は変えない。ロックの理由は利用者に出さない(FNC-001 の例外と境界)。
- ロックの回数(5 回)と時間(30 分)は変えない。
- ログの出し先(標準出力)と書式の形(`%(asctime)s %(levelname)s %(name)s %(message)s`)は変えない。
- 監視の仕組みへの連携は作らない。

## 受入基準

要件定義でロックの行の FR に番号を振り、受入基準の参照を付け替えた。ロックが掛かった時の行は「ロックの行」の FR(FR-025)、ロック中の試みの行は「ロック中の行」の FR(FR-026)である。同じ試みの「ログインに失敗した」の行も併せて出す(質問 Q-04 の答え)。

## リスク判定と実施計画

段階は重要(major)と判定する。該当した因子は次の 2 つである。

- 利用者から見える仕様の変更(visible): 運用の担当が読むログに、新しい種類の行が出る。要件に FR を足す(Q-03)。
- 認証・認可・個人情報(auth): ログインの判定の業務の層(`authenticate`)の振る舞いを変える。ロックの行は、社員番号が登録済みでロック中であることをログに出す。

因子の再判定(レビュー役が plan.md を読まずに判定)は、auth を該当、visible を非該当とした。理由は「画面と API の応答は変わらない」である。visible を外しても段階は重要のままで、通すフェーズも変わらない。下げる向きの食い違いなので、visible を残して人の承認で決める。

当たらない因子と根拠は次のとおりである。

- 意図の抜け(intent): 場面と範囲を依頼元に確かめた(Q-01・Q-02)。
- データ構造の変更・データ移行(data): テーブルは変えない。
- 外部連携(external): ログは標準出力に出すだけで、監視の仕組みへの連携は作らない。
- 約束・予算・期限(commitment): personal のため既定でオフである。
- 影響範囲の広さ(wide): 変える所はコード 3 ファイル・文書 2 ファイルと、テストである。500 行に届かない。
- 新しい作り・依存(new): 既存のロガーと既存の列を使う。新しい依存は足さない。

## 決定

- D-01 〔ロックの行の FR(FR-025)・ロック中の行の FR(FR-026)〕 ロックの区別の渡し方。
  - `authenticate` は、試みの結果を 1 つの型で返す。結果は、成功・失敗・ロックした・ロック中の 4 つである。
  - ログの行は API の層だけが出す。
  - 利用者を持つのは成功の結果だけである。API の層は 4 つの場合を残さず分け、漏れは pyright の strict で見つける。
  - 理由は、業務の判定を業務の層の 1 か所に保ち、ログの出口を API の層にそろえたままにできるためである。
  - 選ばなかった案 1: 業務の層がロックの行を出す。ログの出口が 2 つの層に分かれ、失敗の行とロックの行の順が層をまたぐ。
  - 選ばなかった案 2: API の層が、呼ぶ前と後のロックの終わる時刻を比べる。ロック中かの判定(時刻の比べ方)を 2 か所に持つことになる。
  - 選ばなかった案 3: ロックを例外で知らせる。方式設計は、想定した誤りを例外にしないと定めている。
  - 選ばなかった案 4: 利用者と結果の組を返す。「利用者がなくて成功」のような、ありえない組み合わせを型が許す(設計の反証役の指摘)。
- D-02 〔ロックの行の FR(FR-025)・ロック中の行の FR(FR-026)〕 ロックの行の順と形。
  - ロックの行は、同じ試みの「ログインに失敗した」の行の後に出す。
  - ロガーは今と同じ `app.auth`、水準は INFO である。
  - 文の形は今の行と同じ「<決まった語> 社員番号=<社員番号>」にする。
  - 理由は、運用の担当が今の行と同じ形で読め、検索の語だけで見分けられるためである。
  - 社員番号は今の行と同じ関数で書く。数字 6 桁は引用符つきで出る。
  - 見分けは決まった語だけで足りる。行の順は、テスト項目 TC-01 と TC-02 で確かめる(実装計画で決めた)。
