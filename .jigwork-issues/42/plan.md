# Issue 42 ログインのロックが掛かったことを、ログで見分けられるようにする

## 理解の要約

- 何を: ログインのロックが掛かった時と、ロック中にログインを試みた時に、ふつうの失敗と見分けられる行をログに出す。
- なぜ: 今はどちらも「ログインに失敗した 社員番号=…」の 1 行だけで、運用の担当がロックに気づけないため。
- どこまで: 要件に FR を足し、方式設計のログの決まりを直し、ログの行を出すコードとテストを足す。
- 画面・API の応答・テーブル・ロックの回数と時間は変えない。

## スコープ

- ロックが掛かった時(5 回目の誤り)に、ロックが掛かったと分かる行をログに出す。
- ロック中にログインを試みた時に、ロック中の試みと分かる行をログに出す。
- ロックが掛かった・ロック中の区別を、業務の層 `authenticate`(`backend/app/auth/service.py`)からログの行を出す所へ渡す。渡し方は設計で決める。
- 機能要件「ログインする」(FNC-001、`docs/requirements/functions/FNC-001.md`)に、ロックの行を出す FR を足す(作業者の質問「ロックの行の決まりの置き場」(Q-03)の答え)。
- 方式設計 `docs/internal/architecture.md` の「例外とログ」に、ロックの行の決まりを足す。
- 同じ方式設計の認証の節に、ロックの区別の渡し方を足す。
- ロックの行のテストと、ロックの行にパスワードと印が出ないことのテストを足す。
- コードの説明文(`backend/app/api/auth.py`・`backend/app/log.py` の docstring)を合わせる。実装のレビューで確かめる。

## スコープ外

- ロックの解除(ロックが終わった後の最初の試みで回数を 0 に戻す時)の行は足さない(依頼元の質問「解除の行」(Q-02)の答え)。要るなら別の Issue にする。
- ログインの状態の切れの行は足さない。
- 登録なし・形の誤り・誤ったパスワード(1〜4 回目)・役割なしの失敗は、今の「ログインに失敗した」の行のまま分けない。
- 画面の文と API の応答(401 と共通の文)は変えない。ロックの理由は利用者に出さない(FNC-001 の例外と境界)。
- ロックの回数(5 回)と時間(30 分)は変えない。
- ログの出し先(標準出力)と書式の形(`%(asctime)s %(levelname)s %(name)s %(message)s`)は変えない。
- 監視の仕組みへの連携は作らない。

## 受入基準

要件定義でロックの行の FR に番号を振ったら、次の受入基準の参照をその FR に付け替える。

- 付け替える受入基準: 「掛かった時の行」(AC-01)・「ロック中の試みの行」(AC-02)・「正本の記述」(AC-06)。

ロックの行と同じ試みで「ログインに失敗した」の行を併せて出すかは、要件定義で決めて AC-01 と AC-02 に書き足す。

- AC-01 〔5 回誤るとロックする FR(FR-003)〕 前提: 登録済みの利用者で、パスワードを続けて 4 回誤った。操作: 誤ったパスワードで 5 回目のログインをする。結果: ロックが掛かったと分かる決まった語と社員番号を含む行が、ログに 1 行出る。この語は、ふつうの失敗の行に含まれない。
- AC-02 〔ロック中は数えない FR(FR-020)〕 前提: ロック中の利用者。操作: 正しいパスワードと誤ったパスワードで、1 回ずつログインする。結果: 試みごとに、ロック中の試みと分かる決まった語と社員番号を含む行が、ログに 1 行ずつ出る。この語は、ふつうの失敗の行とロックが掛かった時の行に含まれない。
- AC-03 〔誤りは共通の文の FR(FR-002)・役割なしの FR(FR-023)・形の誤りの FR(FR-024)〕 前提: ロックされていない。操作: 誤ったパスワード・登録のない社員番号・数字 6 桁でない社員番号・役割を持たない利用者で、1 回ずつログインする。結果: どれも「ログインに失敗した」の行だけが出る。AC-01 と AC-02 の語を含む行は出ない。
- AC-04 〔誤りは共通の文の FR(FR-002)〕 前提: AC-01 と AC-02 の操作。結果: 応答は 401 で、エラーの文は FR-002 の受入基準 1(FR-002-AC-01)と同じである(変更前と同じ)。
- AC-05 前提: AC-01 と AC-02 の操作。結果: ログの全体に、送ったパスワードとログインの状態の印が含まれない。
- AC-06 前提: 変更後のリポジトリ。操作: FNC-001 と方式設計を読む。結果: 次の 3 つがある。
  - ロックの行を定める FR と、その受入基準。
  - 方式設計の「例外とログ」の、ロックの行の決まり。
  - 方式設計の認証の節の、ロックの区別の渡し方。
- AC-07 テストの手順 `.jigwork-test.json` のテストがすべて通る。

## 影響範囲

- コード: `backend/app/auth/service.py`(`authenticate`)、`backend/app/api/auth.py`(ログの行と docstring)、`backend/app/log.py`(docstring)。
- テスト: ロックの行のテストを足す。既存の `backend/tests/test_login_log_redaction.py` と `backend/tests/test_auth_session.py` は「ログインに失敗した」の文言を前提にしている。この前提が崩れないことを確かめる。
- ロックのテスト(`backend/tests/test_i38_tc03_lock*.py`)は API を通して確かめる。`authenticate` を直に呼ぶテストは無い(調査メモ(R-01)の 5 節)。
- 文書: `docs/requirements/functions/FNC-001.md`、`docs/internal/architecture.md`(例外とログ・認証の節)。
- 画面・帳票・API の形・テーブル・バッチ・外部連携・設定・権限: なし。
- 調査メモ: [R-01](research/R-01.md)。

## 前提一覧

- 🔵 「ログインに失敗した」の行は `backend/app/api/auth.py:138` の 1 か所だけで、INFO で出る(調査メモ(R-01))。
- 🔵 `authenticate` は `User | None` だけを返し、ロックの区別を持たない。呼び出し元は `backend/app/api/auth.py:136` の 1 か所だけである(調査メモ(R-01))。
- 🔵 ロックの区別に要る値は、既存の列 `users.locked_until` と `users.failed_login_count` で足りる。テーブルは変えない(調査メモ(R-01))。
- 🔵 登録のない社員番号はロックしない(FNC-001 の例外と境界)。登録のない社員番号でロックの行は出ない。
- 🔵 ロックの行は社員番号を出す。方式設計は「ログインの成否と社員番号は残す」と定める(`docs/internal/architecture.md:103`)。
- 🟡 ログを読むのは運用の担当だけである(推定)。
  - 根拠は、ログを標準出力にだけ出す決まり(`docs/internal/architecture.md:103`)である。
  - ロックの行は「その社員番号は登録済み」と分かる情報を持つ。ログが利用者に見えないなら、列挙の手掛かりにならない。
- 🟡 運用の担当は、決まった語の文字列の検索でロックの行を見つける(推定)。行の文言と水準(INFO か WARNING か)は要件定義と設計で決める。

## 質問と回答

- Q-02 【依頼元】「ロックの解除の行も今回の範囲に入れますか?」 回答: 「入れない」。
- Q-03 【作業者】「ロックの行の決まりは、どの正本に書きますか?」 回答: 「要件 FNC-001 に FR を足す」。

## リスク判定と実施計画

段階は重要(major)と判定する。該当した因子は次の 2 つである。

- 利用者から見える仕様の変更(visible): 運用の担当は、このシステムのログの利用者である。その運用の担当が読むログに、新しい種類の行が出る。要件に FR を足す(Q-03)。
- 認証・認可・個人情報(auth): ログインの判定の業務の層(`authenticate`)の振る舞いを変える。ロックの行は、社員番号が登録済みでロック中であることをログに出す。

因子の再判定(レビュー役が plan.md を読まずに判定)は、auth を該当、visible を非該当とした。理由は「画面と API の応答は変わらない」である。visible を外しても段階は重要のままで、通すフェーズも変わらない。下げる向きの食い違いなので、visible を残して人の承認で決める。

当たらない因子と根拠は次のとおりである。

- 意図の抜け(intent): 場面と範囲を依頼元に確かめた(Q-01・Q-02)。
- データ構造の変更・データ移行(data): テーブルは変えない。
- 外部連携(external): ログは標準出力に出すだけで、監視の仕組みへの連携は作らない。
- 約束・予算・期限(commitment): personal のため既定でオフである。
- 影響範囲の広さ(wide): 変える所はコード 3 ファイル・文書 2 ファイルと、テストである。500 行に届かない。
- 新しい作り・依存(new): 既存のロガーと既存の列を使う。新しい依存は足さない。

## 正本への影響

### 要件定義

- 機能要件「ログインする」(FNC-001)に、ロックが掛かった時の行を出す FR を足し、受入基準を付ける。番号は要件定義で振る(今の最大は「同時のログイン」の次の「形の誤り」の FR(FR-024))。
- 同じ FNC-001 に、ロック中の試みの行を出す FR を足し、受入基準を付ける。
- 用語集に「ログ」を足すかは要件定義で決める。

### 設計

- 方式設計 `docs/internal/architecture.md` の「例外とログ」に、ロックの行の文言・水準・載せる項目と、載せないもの(パスワード・印)を足す。
- 同じ文書の認証の節に、ロックの区別の渡し方を足す。
