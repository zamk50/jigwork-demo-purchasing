# Issue 42 ログインのロックが掛かったことを、ログで見分けられるようにする

## 理解の要約

- 何を: ログインのロックが掛かった時と、ロック中にログインを試みた時に、ふつうの失敗と見分けられる行をログに出す。
- なぜ: 今はどちらも「ログインに失敗した 社員番号=…」の 1 行だけで、運用の担当がロックに気づけないため。
- どこまで: 要件に FR を足し、方式設計のログの決まりを直し、ログの行を出すコードとテストを足す。
- 画面・API の応答・テーブル・ロックの回数と時間は変えない。

## スコープ

- ロックが掛かった時(5 回目の誤り)に、ロックが掛かったと分かる行をログに出す。
- ロック中にログインを試みた時に、ロック中の試みと分かる行をログに出す。
- 業務の層 `authenticate`(`backend/app/auth/service.py`)の結果に、ロックが掛かった・ロック中の区別を持たせる。区別の渡し方は設計で決める。
- 機能要件 `docs/requirements/functions/FNC-001.md` に、ロックの行を出す FR を足す(作業者の質問 Q-03 の答え)。
- 方式設計 `docs/internal/architecture.md` の「例外とログ」に、ロックの行の決まりを足す。
- ロックの行のテストと、ロックの行にパスワードと印が出ないことのテストを足す。
- コードの説明文(`backend/app/api/auth.py`・`backend/app/log.py` の docstring)を合わせる。

## スコープ外

- ロックの解除(ロックが終わった後の最初の試みで回数を 0 に戻す時)の行は足さない(依頼元の質問 Q-02 の答え)。要るなら別の Issue にする。
- ログインの状態の切れの行は足さない。
- 登録なし・形の誤り・誤ったパスワード(1〜4 回目)・役割なしの失敗は、今の「ログインに失敗した」の行のまま分けない。
- 画面の文と API の応答(401 と共通の文)は変えない。ロックの理由は利用者に出さない(FNC-001 の例外と境界)。
- ロックの回数(5 回)と時間(30 分)は変えない。
- ログの出し先(標準出力)と書式の形(`%(asctime)s %(levelname)s %(name)s %(message)s`)は変えない。監視の仕組みへの連携は作らない。

## 受入基準

- AC-01 〔FR-003〕 前提: 登録済みの利用者で、パスワードを続けて 4 回誤った。操作: 誤ったパスワードで 5 回目のログインをする。結果: ロックが掛かったと分かる決まった語と社員番号を含む行がログに 1 行出る。この語は、ふつうの失敗の行には含まれない。
- AC-02 〔FR-020〕 前提: ロック中の利用者。操作: 正しいパスワードと誤ったパスワードで、それぞれ 1 回ずつログインする。結果: 試みごとに、ロック中の試みと分かる決まった語と社員番号を含む行がログに 1 行ずつ出る。この語は、ふつうの失敗の行とロックが掛かった時の行には含まれない。
- AC-03 〔FR-002〕 前提: ロックされていない。操作: 誤ったパスワードで 1 回、登録のない社員番号で 1 回、数字 6 桁でない社員番号で 1 回ログインする。結果: どれも「ログインに失敗した」の行だけが出て、AC-01 と AC-02 の語を含む行は出ない。
- AC-04 〔FR-003〕 前提: AC-01 と AC-02 の操作。結果: 応答は 401 で、FR-002-AC-01 と同じエラーの文である。変更の前と同じである。
- AC-05 前提: AC-01 と AC-02 の操作。結果: ログの全体に、送ったパスワードとログインの状態の印が含まれない。
- AC-06 前提: 変更後のリポジトリ。操作: FNC-001 と方式設計を読む。結果: ロックの行を定める FR と、その受入基準と、方式設計の「例外とログ」のロックの行の決まりがある。
- AC-07 テストの手順 `.jigwork-test.json` のテストがすべて通る。

## 影響範囲

- コード: `backend/app/auth/service.py`(`authenticate` の結果)、`backend/app/api/auth.py`(ログの行と docstring)、`backend/app/log.py`(docstring)。
- テスト: ロックの行のテストを足す。既存の `backend/tests/test_login_log_redaction.py`・`backend/tests/test_auth_session.py` の「ログインに失敗した」の前提が崩れないことを確かめる。ロックのテスト(`backend/tests/test_i38_tc03_lock*.py`)は API を通すため、`authenticate` の型の変更の影響を受けない見込みである。
- 文書: `docs/requirements/functions/FNC-001.md`、`docs/internal/architecture.md`(例外とログ)。
- 画面・帳票・API の形・テーブル・バッチ・外部連携・設定・権限: なし。
- 調査メモ: [R-01](research/R-01.md)。

## 前提一覧

- 🔵 「ログインに失敗した」の行は `backend/app/api/auth.py:138` の 1 か所だけで、INFO で出る(R-01)。
- 🔵 `authenticate` は `User | None` だけを返し、ロックの区別を持たない。呼び出し元は `backend/app/api/auth.py:136` の 1 か所だけである(R-01)。
- 🔵 ロックの区別に要る値は、既存の列 `users.locked_until` と `users.failed_login_count` で足りる。テーブルは変えない(R-01)。
- 🔵 登録のない社員番号はロックしない(FNC-001 の例外と境界)。登録のない社員番号でロックの行は出ない。
- 🔵 ロックの行は社員番号を出す。今の失敗の行も社員番号を出しており、方式設計は「ログインの成否と社員番号は残す」と定める(`docs/internal/architecture.md:103`)。
- 🟡 ログを読むのは運用の担当だけで、利用者には見えない。ロックの行が「その社員番号は登録済み」と分かる情報を持っても、利用者の列挙の手掛かりにはならない(推定。方式設計の前提に合わせた)。
- 🟡 運用の担当は、決まった語の文字列の検索でロックの行を見つける。行の文言と水準(INFO か WARNING か)は要件定義と設計で決める(推定)。

## 質問と回答

- Q-01 【依頼元】「ロックについて、ふつうの失敗と見分けられる行を出すのはどの場面にしますか?」 回答: 「掛かった時とロック中の試み」。
- Q-02 【依頼元】「ロックが終わった後の最初の試みで回数が 0 に戻る時(ロックの解除)は、今ログに何も出ません。これも今回の範囲に入れますか?」 回答: 「入れない」。
- Q-03 【作業者】「ロックの行の決まりは、どの正本に書きますか?」 回答: 「要件 FNC-001 に FR を足す」。

## リスク判定と実施計画

段階は重要(major)と判定する。該当した因子は次の 2 つである。

- 利用者から見える仕様の変更(visible): 運用の担当が読むログに、新しい種類の行が出る。要件に FR を足す(Q-03)。
- 認証・認可・個人情報(auth): ログインの判定の業務の層(`authenticate`)の結果の型を変える。ロックの行は、社員番号が登録済みでロック中であることをログに出す。

当たらない因子と根拠は次のとおりである。

- 意図の抜け(intent): 場面と範囲を依頼元に確かめた(Q-01・Q-02)。
- データ構造の変更・データ移行(data): テーブルは変えない。
- 外部連携(external): ログは標準出力に出すだけで、監視の仕組みへの連携は作らない。
- 約束・予算・期限(commitment): personal のため既定でオフである。
- 影響範囲の広さ(wide): 差分はテストを含めて 200 行ほどの見込みである。
- 新しい作り・依存(new): 既存のロガーと既存の列を使う。新しい依存は足さない。

## 正本への影響

### 要件定義

- FNC-001 に、ロックが掛かった時の行を出す FR を足す(番号は要件定義で振る。今の最大は FR-024)。受入基準を付ける。
- FNC-001 に、ロック中の試みの行を出す FR を足す。受入基準を付ける。
- 用語集に「ログ」を足すかは要件定義で決める。

### 設計

- 方式設計 `docs/internal/architecture.md` の「例外とログ」に、ロックの行の文言・水準・載せる項目と、載せないもの(パスワード・印)を足す。
- 同じ文書の認証の節に、`authenticate` がロックの区別を返すことを足す。
