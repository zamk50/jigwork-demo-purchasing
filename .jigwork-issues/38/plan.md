# Issue 38 購買と在庫のシステムを作り始める(要件の確認と土台)

## 理解の要約

- 何を: ログイン・ログアウトと、4 つの役割に応じたメニューを作る。役割は社員・上長・購買担当・管理者である。仕様概要 `docs/spec.md` のシステムの最初の一歩である。
- なぜ: 依頼元(総務部)が、まず仕様の分からない所を確かめ、ログインと役割から作り始めることを求めているため。
- どこまで: アプリの土台(API のサーバー・画面・DB・テストの道具)を、依頼側が決めた技術で置く。メニューの先の業務の画面は作らない。4 役割の利用者は初期データで用意する。
- 正本の文書(要件と設計)を、この範囲について書き始める。

## スコープ

- 仕様の穴を依頼元に確かめ、要件を正本に書く(システム概要・機能要件・非機能要件・用語集)。
- 方式設計 `docs/internal/architecture.md` に技術の選定と横断の方式を書く。
- 土台を置く。API のサーバーは FastAPI、画面は React + Vite、DB は PostgreSQL と Alembic である。
- 自前の ID とパスワードによるログインとログアウトを作る。
- 役割に応じたメニューを出す。
- 利用者・役割・利用者と役割の対応のテーブルを作り、4 役割の利用者を初期データで入れる。
- テストの手順 `.jigwork-test.json` と、型の検査・lint・テストの道具を置く。

## スコープ外

- メニューの先の業務の画面(品目・購入依頼・決裁・発注・入荷・在庫・夜間の処理・取り込み・書き出し・集計)。次からの Issue で作る。
- 管理者が利用者と役割を登録・変更する画面。次の Issue の候補である(Q-01 の答え)。
- 社内の既存の認証(AD・LDAP など)とのつなぎ込み(Q-02 の答え)。
- 本番(Azure)への配置と、配置の手順。
- テーブル定義書の Excel(受け入れたリスクの B3。テーブルは設計書の文で書く)。
- 画面のモックアップと撮影(受け入れたリスクの B2)。

## 受入基準

- AC-1: 4 役割それぞれの初期データの利用者が、ログイン画面で ID とパスワードを入れてログインできる。ログインの後に、その役割に応じたメニューが出る。メニューの項目は、要件定義で決めた機能要件のとおりである。
- AC-2: 誤ったパスワード、または登録のない ID ではログインできず、ログイン画面にエラーが出る。
- AC-3: ある役割の利用者のメニューに、その役割に許していない項目が出ない。メニューを返す API も、その利用者の役割に許した項目だけを返す。
- AC-4: ログインしていない状態でメニューの画面を開くと、ログイン画面に移る。ログインが要る API をログインせずに呼ぶと、401 が返る。
- AC-5: ログアウトした後は、メニューの画面と API の両方で、もう一度ログインが要る。
- AC-6: DB にはパスワードのハッシュだけがあり、平文のパスワードはない。リポジトリには本番の秘密(本番のパスワード・鍵・接続文字列)がない。
- AC-7: この Issue で作るテーブルと列のすべてに、日本語の論理名のコメントがある。テーブルにはテーブル番号(例 T001)がある。根拠は `docs/spec.md` の「守ってほしいこと」である。
- AC-8: テストの手順 `.jigwork-test.json` を流すと、すべて通る。手順には pytest・vitest・Playwright のテストがある。pyright(strict)・tsc・Ruff・Oxlint の検査もある。
- AC-9: 要件(システム概要・機能要件・非機能要件・用語集)と設計(方式設計ほか)の正本に、この範囲の中身が書かれ、`jig check` が緑である。

## 質問と回答

- Q-01 【依頼元】この Issue の範囲はどこまでにするか。答え: ログインとメニューだけ。メニューの先の画面は作らず、4 役割の利用者は初期データで用意する。利用者の管理画面は次の Issue。
- Q-02 【依頼元】ログインの方式はどれにするか。答え: 自前の ID とパスワード。
- Q-03 【作業者】技術をどう決めるか。答え: 依頼側で決めてある。これに従う。
  - バック: Python 3.12、FastAPI(uvicorn)、SQLAlchemy 2 + Alembic。DB は PostgreSQL(本番は Azure Database for PostgreSQL、テストは WSL2 の PostgreSQL を一時に立てる)。
  - 画面: TypeScript、React + Vite(1 枚のページのアプリ)、shadcn/ui(Radix)+ Tailwind v4、表は TanStack Table。API の型は FastAPI の OpenAPI から生成する。
  - 型: pyright(strict)、tsc。lint と整形: Ruff、Oxlint。
  - テスト: pytest、vitest(画面の通しは Playwright)。
  - 道具の版は mise、Python の依存は uv、画面の依存は pnpm。
  - 細かい版と構成は方式設計に書き、方針決めの承認で確かめる。
- Q-04 【作業者】テストの道具をどう用意するか。答え: 人が入れる。uv と pnpm は mise で入れ済みで、リポジトリの `mise.toml` で版を指して使う。新しく入れるのは PostgreSQL だけで、実装計画に apt の手順を書けば人が sudo で入れる。入るまで実装は始めない。
