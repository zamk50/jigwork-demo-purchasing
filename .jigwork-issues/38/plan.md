# Issue 38 購買と在庫のシステムを作り始める(要件の確認と土台)

## 理解の要約

- 何を: ログイン・ログアウトと、4 つの役割に応じたメニューを作る。役割は社員・上長・購買担当・管理者である。仕様概要 `docs/spec.md` のシステムの最初の一歩である。
- なぜ: 依頼元(総務部)が、まず仕様の分からない所を確かめ、ログインと役割から作り始めることを求めているため。
- どこまで: アプリの土台(API のサーバー・画面・DB・テストの道具)を、依頼側が決めた技術で置く。メニューの先の業務の画面は作らない。4 役割の利用者は初期データで用意する。
- 正本の文書(要件と設計)を、この範囲について書き始める。

## スコープ

- 仕様の穴を依頼元に確かめ、要件を正本に書く(システム概要・機能要件・非機能要件・用語集)。
- 方式設計 `docs/internal/architecture.md` に技術の選定と横断の方式を書く。
- 土台を置く。API のサーバーは FastAPI、画面は React + Vite、DB は PostgreSQL と Alembic である。
- 自前の ID とパスワードによるログインとログアウトを作る。
- 役割に応じたメニューを出す。
- 利用者・役割・利用者と役割の対応のテーブルを作り、4 役割の利用者を初期データで入れる。
- テストの手順 `.jigwork-test.json` と、型の検査・lint・テストの道具を置く。

## スコープ外

- メニューの先の業務の画面は、次からの Issue で作る。品目・購入依頼・決裁・発注・入荷・在庫・夜間の処理・取り込み・書き出し・集計の画面である。
- 管理者が利用者と役割を登録・変更する画面は、次の Issue の候補である(範囲の質問 Q-01 の答え)。
- 認証は自前で持つ。社内の既存の認証(AD・LDAP など)とはつながない(認証の方式の質問 Q-02 の答え)。
- 本番(Azure)への配置と、配置の手順は、後の Issue で扱う。
- テーブルは設計書の文で書く。テーブル定義書の Excel は後に回す。jigwork が延ばした「ER 図とテーブル定義書」(B3)の受け入れたリスクである。
- 画面は設計書の文で書く。モックアップと撮影は、jigwork が延ばした「モックアップと撮影」(B2)の受け入れたリスクとして後に回す。
- スマホ向けに画面を作り込むことは、決裁と入荷の画面の Issue で扱う。この Issue のログインとメニューがスマホのブラウザで使えるかは、要件定義で決める。

## 受入基準

メニューの項目と役割の持ち方(1 人が複数の役割を持つか)は、要件定義で決めて機能要件に書く。以下の基準の「項目表」は、その機能要件の役割とメニューの項目の対応表を指す。

- AC-1 ログインとメニュー: 4 役割それぞれの初期データの利用者が、ログイン画面で ID とパスワードを入れてログインできる。
  - ログインの後に、メニューの画面が出る。
  - メニューの画面の項目は、項目表のその利用者の役割の行と一致する。
  - ログイン中の利用者を返す API は、その利用者の ID・氏名・役割を返す。
- AC-2 ログインの失敗: 誤ったパスワードではログインできない。登録のない ID でもログインできない。どちらもログイン画面にエラーが出る。
- AC-3 役割による出し分け: メニューを返す API は、項目表のその利用者の役割の行の項目だけを返す。ほかの役割だけに許した項目は、画面にも API にも出ない。
- AC-4 ログインしていないとき: ログインしていない状態でメニューの画面を開くと、ログイン画面に移る。ログインが要る API をログインせずに呼ぶと、401 が返る。
- AC-5 ログアウト: ログアウトした後にメニューの画面を開くと、ログイン画面に移る。ログアウトした後にメニューを返す API を呼ぶと、401 が返る。
- AC-6 秘密の扱い: DB の利用者のテーブルにはパスワードのハッシュだけがあり、平文のパスワードはない。
  - DB の接続先とセッションの鍵は、リポジトリの外(環境変数など)から読む。どちらも無いと、API のサーバーは起動の時に止まる。
  - 秘密を探す道具(gitleaks)でリポジトリを走査すると、指摘が 0 件である。
  - 初期データの利用者のパスワードの扱いは、要件定義で決めたとおりである。
- AC-7 テーブルの論理名: 設計で決めたテーブルと列のすべてに、日本語の論理名のコメントがある。テーブルにはテーブル番号(例 T001)がある。確かめ方は、DB のカタログを引くテストで、欠けが 0 件であることである。根拠は `docs/spec.md` の「守ってほしいこと」である。
- AC-8 テストと検査: テストの手順 `.jigwork-test.json` を流すと、すべて通る。手順には pytest・vitest・Playwright のテストがある。pyright(strict)・tsc・Ruff・Oxlint の検査もある。
- AC-9 正本の文書: 要件と設計の正本に、この範囲の中身がある。要件はシステム概要・機能要件・非機能要件・用語集で、設計は方式設計ほかである。`jig check` が緑である。

## 決定

- D-01 〔FR-005・FR-006・FR-013〕 ログインの状態は DB の表に持ち、ブラウザには乱数の印をクッキーで渡す。
  - 理由: ログアウトでその場で無効にでき、操作のない 30 分も正確に測れる。
  - 選ばなかった案: 署名つきのトークン(JWT)。DB を引かずに済むが、無効にするには無効の一覧が要る。操作のない時間で切るにも、トークンを出し直し続ける作りが要る。
  - CSRF には、SameSite=Lax と、状態を変える API の JSON だけの受け付けで備える。
- D-02 〔FR-010・NFR-005〕 パスワードのハッシュは argon2id で作る。
  - 理由: 今の推奨の方式で、メモリを使うので総当たりに強い。
  - 選ばなかった案: bcrypt。広く使われるが、72 バイトを超える部分を捨てる。PBKDF2 は GPU での総当たりに弱い。
- D-03 〔FR-016・FR-018・FR-019〕 メニューの項目表は、API のサーバーのコードの定数に持つ。
  - 理由: 項目は画面とともに Issue ごとに足すもので、行き先もコードにある。項目を画面で編集する要件はない。
  - 選ばなかった案: DB の表に持つ。管理者が編集できるが、編集の画面もなく、移行と初期データが増える。
- D-04 〔NFR-006・FR-010〕 4 利用者は、初期データを入れるコマンドで入れる。部署と役割は Alembic の移行で入れる。
  - 理由: 利用者のパスワードは環境変数から読む。移行に秘密の読み込みを入れると、移行が環境で変わるためである。
  - 選ばなかった案: 利用者も移行で入れる。コマンドは 1 つで済むが、移行が秘密の環境変数に頼る。
- D-05 〔FR-001・FR-007・FR-011・FR-012・FR-015・FR-019〕 画面は 2 枚で、文で書く(モックアップは延ばした)。
  - ログイン画面 `/login`: 社員番号・パスワードの欄と、ログインのボタンを縦に並べる。誤りの文はボタンの上に出す。
  - メニューの画面 `/menu`: 上に氏名・部署とログアウトのボタンを出す。その下に、役割ごとの見出しと項目を並べる。
  - 準備中の項目は、押せないボタンに「準備中」の札を添えて出す。
  - `/` は `/menu` に移る。ログインの要る画面は、ログインしていなければ `/login` に移る。
- D-06 〔NFR-011〕 テーブルのコメントは「T001 部署」の形で、テーブル番号と論理名を持つ。
  - 理由: PostgreSQL のコメントだけで、番号と論理名が引ける。延ばしたテーブル定義書の Excel を後で作るときにも使える。
  - 選ばなかった案: 番号を物理名に入れる(`t001_departments`)。SQL が読みにくくなる。
  - `alembic_version` は道具の表なので、コメントの検査から外す。
- D-07 〔Q-16〕 Python も `mise.toml` で 3.12 を指す。人が自分の端末で `mise install` を流す手順を、PostgreSQL を入れる手順と一緒に実装計画に書く。
- D-08 〔FR-003・FR-004〕 誤った回数の排他は、利用者の行を `SELECT … FOR UPDATE` で押さえてから数える。
  - 理由: 照合・加算・ロックの判定を、1 つの行の錠の中で順に書ける。120 人の規模では待ちは問題にならない。
  - 選ばなかった案: 1 つの UPDATE 文で回数を足し、結果でロックを決める。錠は短いが、ロックの終わりで 0 に戻す判定まで SQL に詰めることになり、読みにくい。
- D-09 〔FR-002・FR-003・FR-023・FR-024〕 ログインの失敗は、どの経路でも argon2id の照合を 1 回行ってから返す。
  - 理由: ロック中・登録なし・形の誤りの応答が速いと、時間で登録の有無を推し量れる。
  - 選ばなかった案: 照合の要らない失敗は照合せずに返す。速いが、上の漏れがある。

### テストの手順の形

- `test` には、pytest(`backend/`)・vitest(`frontend/`)・Playwright(`frontend/`)を、実行器を直接呼ぶ形で並べる。
- `install` は `uv sync --frozen --no-build` と `pnpm install --frozen-lockfile --ignore-scripts` にする。
- `tool_path` は mise の installs の下と、`/usr/lib/postgresql/18/bin` にする。
- 型の検査と lint は、実行器ではないので手順に直接は書けない。pytest のテスト(TC-19)から流す(Q-19 の答え)。
- 手順のファイルを置くと、人の確認が要るブロックになる。次の人のゲートで人が通す。

### 分かっているリスク

- 画面の通しのテストは、jig gate の中で一時の DB と 2 つのサーバーを立てる。サンドボックスで口を開けられなければ、T-6 で止めて人に上げる。
- Playwright のブラウザは、人の端末のキャッシュに入る。jig gate から読めなければ、設定 `quality.test_spec` で人に足してもらう。

## 推奨から外した箇所

- 影響範囲の広さ(wide)では Issue の分割を勧める決まりがある。この Issue は分割しない。
  - 理由: Issue の題名が「要件の確認と土台」で、依頼元は土台と最初の画面を 1 つで作ることを求めている。
  - 分けるなら: 「土台」と「ログインとメニュー」の 2 つになる。
- 因子の再判定で、意図の抜け(intent)が該当とされた。Issue が「仕様で分からないところを確かめてから」と求めているためである。factors に intent を足した。段階は重要のままで変わらない。
- 因子の再判定で、約束・予算・期限(commitment)は「該当のおそれ」とされた。personal の既定でオフのため、非該当のままにした。
- 方式設計の「技術の選定」と「版」は、設計のフェーズを待たずに方針決めで書いた。技術の質問(Q-03)の答えが、方針決めの承認で確かめることを求めたため。横断の方式は設計で書く。
- 持ち帰り中の質問はない。
- 重要の段階では、実装計画の末に途中の draft PR を勧める決まりがある。人は作らないと答えた(Q-18)。要件・設計・実装計画は、実装前の承認の画面で見る。
