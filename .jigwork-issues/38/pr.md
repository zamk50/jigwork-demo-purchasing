## 概要
仕様概要 `docs/spec.md` のシステムの最初の一歩として、土台とログイン・ログアウト・役割に応じたメニューを作った。

- 土台: API のサーバーは FastAPI(`backend/`)、画面は React と Vite(`frontend/`)である。
- DB は PostgreSQL で、移行は Alembic である。テストの手順は `.jigwork-test.json` に置いた。
- 認証: 自前の社員番号とパスワードでログインする。パスワードは argon2id のハッシュだけを持つ。ログインの状態は DB に持ち、クッキーで指す。5 回の誤りで 15 分ロックする。操作のない 30 分か、ログインから 8 時間で切れる。
- メニュー: 社員・上長・購買担当・管理者の 4 役割に応じた項目を、API と画面の両方で出し分ける。
- テーブル: 5 つのテーブル(T001〜T005)のすべてのテーブルと列に、日本語の論理名のコメントを付けた。初期データのコマンドで 4 役割の利用者を入れる。
- 秘密: DB の接続先とセッションの鍵は環境変数から読み、無いと起動の時に止まる。DB の接続には hide_parameters を付け、ログと例外の文に SQL の値を載せない。
- 正本の文書: システム概要・機能要件(FNC-001〜FNC-003)・非機能要件・用語集・方式設計 `docs/internal/architecture.md`・画面共通規則を書いた。

受入基準 9 つ(AC-1〜AC-9)は検証(V-02)ですべて合格した。証拠は `.jigwork-issues/38/evidence/V-02/` にある。jig gate はテスト 153 件で失敗 0 件だった。gitleaks の走査は指摘 0 件だった。

## 意思決定
- ログインの状態は DB に持ち、クッキーで指す(決定 D-01)。
- どの失敗も 401 と同じ文で返し、パスワードの照合を 1 回にそろえる(決定 D-09)。
- 型の検査と lint は、pytest のテストから流す(質問 Q-19 の答え)。道具は Ruff・pyright(strict)・tsc・Oxlint である。
- 社内の既存の認証(AD・LDAP など)とはつながない(質問 Q-02 の答え)。管理者が利用者と役割を登録する画面は次の Issue に回す(質問 Q-01 の答え)。
- gitleaks の誤検知は、記録の中の鍵の形だけを許す狭い許可を `.gitleaks.toml` に置いた(質問 Q-23 の答え)。
