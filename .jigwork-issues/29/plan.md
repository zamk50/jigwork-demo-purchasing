# Issue 29 仕様概要 docs/spec.md を入れる

## 方針決め

### 理解の要約

- 何を: Issue 29 の本文にある「仕様概要」(架空の会社「みなと精機」の、備品・消耗品の購買と在庫のシステム)を、Markdown の文書 `docs/spec.md` としてリポジトリに置く。
- なぜ: 後の Issue(要件定義など)が読む入力にするため。
- どこまで: Issue 本文の区切り線(`---`)の後にある本文を、文の意味を変えずに移す。コードは変えない。

### 前提の一覧

確かめた前提:

- リポジトリにあるのは `README.md` と `.jigwork/` だけで、`docs/` はまだない(`git ls-files` で確かめた)。新しいファイルを足すだけで、既存のファイルとはぶつからない。
- 入力の正本は GitHub の Issue #29 の本文(https://github.com/zamk50/jigwork-demo-purchasing/issues/29)。添付は別にない。
- 本文はもう Markdown(見出し・太字・箇条書き)で書かれている。

仮定のまま残る前提:

- 🟡 `docs/spec.md` の先頭の見出しは、Issue 本文の `## 架空の会社「みなと精機」の、…` を 1 段上げて `#` にする。違っても見出しを直すだけで済む。
- 🟡 文書の先頭に出典(Issue #29 から移したこと)を 1 行添える。要らなければ消すだけで済む。
- 🟡 Issue 本文の区切り線の前にある依頼の文(「依頼元から受け取った…」と箇条 2 つ)は、Issue への指示であって仕様ではないので移さない。

### 受入基準

- AC-1: `docs/spec.md` がリポジトリにあり、Markdown として読める。数えて確かめる: `#` の見出しが 1 つ、`**…**` で始まる段落が 6 つ(目的・使う人・業務の流れ・欲しい機能・データの量・守ってほしいこと)、`- ` の箇条書きが合わせて 28 項(4 + 6 + 10 + 8)。
- AC-2: `docs/spec.md` の本文は、Issue #29 本文の区切り線の後にある「仕様概要」と文の意味が同じである。見出し・目的・使う人(4 役)・業務の流れ(6 項)・欲しい機能(10 項)・データの量・守ってほしいこと(8 項)が、文言を変えずにそろっている。確かめ方: 検証のときに `jig svc issue.get 29` で Issue 本文を取り直し、区切り線(`---`)の後を比較元として `docs/spec.md` と差分を取る。許す差は、見出しの段・出典の 1 行・改行と空白だけ。
- AC-3: この Issue の差分は、文書だけである。基準のコミットからの `git diff --stat` で、`docs/spec.md` と `.jigwork-issues/29/` のほかに変わったファイルがない(jig が書く記録 `.jigwork/records/` は除く)。

### スコープ外

- 仕様の中身を直す・足す・まとめ直す・解釈すること(要件定義は後の Issue)。
- 仕様にある機能の実装、DB・画面・Excel のテンプレートなど、成果物を作ること。
- `README.md` の更新(仕様概要へのリンクを足すことも含む)。
- 依頼元(総務部)の承認を取ること。

### 段階の判定

| 因子 | 判定 | 根拠 |
|---|---|---|
| 意図の抜け | 非該当 | Issue が置き場所(`docs/spec.md`)と中身(本文の仕様概要)と制約(意味を変えない・コードを変えない)を書いており、作るものとずれる余地がない |
